# Better Codex 本地开发版

基于 Better Codex 0.4.18 的本地定制版本。项目资料、任务元信息和看板由 Better Codex 管理；项目规划与工作会话都使用常驻四列工作区：项目列表、所属会话列表、完整 Codex 原生聊天、项目或任务资料。右侧资料可收起，模型、权限和模式沿用原生设置。

## 使用流程

1. 选择项目，核对工作目录及资料，进入“规划”。项目列表与规划页面保持显示；从会话列表选择已有总纲会话，或明确新建一条。新会话显示空白原生输入框；自己选择 `$better-codex-charter` 或需要的 Skill，输入具体要求，再发送。打开页面本身不创建原生线程、不发送预设内容。
2. 用 `$better-codex-charter` 制定或修订总纲，以 `$better-codex-charter-review` 审核需求、范围和业务逻辑，处理必需问题后由用户确认对应版本。确认来自真实用户消息或资料区的“确认总纲”按钮；总纲变更后需要重新确认，审核意见不代替用户确认。
3. 总纲确认后，从规划会话列表选择或新建独立的任务规划会话，用 `$better-codex-plan` 规划任务，再用 `$better-codex-task-review` 核对需求覆盖、必要范围、闭环与依赖。计划包含目标、范围、架构契约、目录职责、依赖、交付物和人工验收步骤。切换会话只更新聊天与归属资料，项目工作区保持显示。
4. 在右侧资料区阅读保存的总纲章节和任务列表，查看每项规划及关联开发任务状态。明确选择“转为开发任务”，或批量转换所选条目到待办（`todo`）；转换不会自动执行任务，重复转换不会重复创建或重置已有任务状态。
5. 在工作看板点击“新建会话”，直接进入当前项目的空白原生会话；同时登记一个工作项，不派发执行或请求模型生成标题。“新建工作项”用于先填写任务信息。第二列按工作任务分组展示各条会话及历史，第三列使用原生聊天，右侧显示任务要求、状态和验收标准。开发时选择 `$better-codex-develop`，添加具体要求和资料并发送；实际开工登记进行中，开发与代码复核完成后登记待审核。
6. 在该任务的工作会话使用 `$better-codex-test` 测试验收。必需技术验收全部通过且无剩余人工项时完成；有人工步骤时保留待审核，由用户在界面确认。验收失败返回进行中等待修复，状态变化不自动派发；缺少必需环境、依赖或证据且无法继续时如实登记阻塞，条件恢复后继续原阶段。

正常聊天回合结束只表示本次回复结束，不等于开发完成或验收通过。任务状态依据真实阶段动作和结果记录更新，开发交付与测试验收各自记录；仅写“完成”或上传报告不会自动把任务设为完成。

一个开发任务可以开启多条工作会话，各自保留文字、Skill、附件、原生线程和未发送草稿。点击任务旁的“新建会话”增加一条，切换只更新选择和页面；同一任务同时只允许一条实际执行，其他会话仍可浏览或编辑草稿。重新开始只将指定会话保留为只读历史，并新建它的后续会话，不替换其他会话。旧执行器中的任务继续保留原有状态与明确移交入口。

总纲、规划和工作会话各自绑定，使用宿主原生聊天组件。一个项目可保留多条规划会话，各自的未发送草稿、Skill 和附件保持隔离；聊天内容仍由 Codex 管理。总纲和任务规划资料在项目内按版本保存，已转换任务保留引用版本。“重新开始”保留旧会话与资料。旧执行器正在运行的任务先显示状态，结束后可在同页移交并继续聊天，打开页面不会停止它。

规划会话列表每条会话旁提供“归档”。点击后归档对应 Codex 原生会话并从本项目列表移出；如果已在首页归档，再点击此处“归档”即可移出残留条目。聊天记录和项目总纲、任务规划资料保留。归档当前会话后切换到剩余会话，列表为空时显示空白输入框；正在运行或发送中的会话需等待完成后归档。

总纲修订后，已转换任务继续引用原确认版本。需要同步时，在任务规划会话明确选择更新相应条目的规划资料；未开始执行的任务按当前版本更新，重复转换本身不会覆盖任务。

工作历史会话用于查看原生消息，输入、开始、重新开始与移交操作受只读限制；打开历史不更改当前任务绑定、状态或执行队列。退出历史后普通原生会话恢复原有交互。历史旁边展示的是当前任务所引用的资料版本，旧记录没有保存当时资料快照时，不能据此还原历史时点的总纲。已在 Codex 中归档的线程会显示宿主的恢复入口，用户明确恢复后才能查看；Better Codex 不自动取消原生归档。

窗口缩窄时右侧资料改为抽屉，聊天保持可用宽度；回到宽屏恢复原来的资料展开偏好。页面重载保留项目、会话、草稿及资料状态，不自动发送或启动任务。

在当前窗口内从首页返回最近项目，直接显示保留着的原生聊天和项目工作区，再恢复会话订阅与更新资料；页面、滚动位置和资料宽度保留。最近已绑定的项目会话不会因为闲置超时被清除。窗口关闭后仍记住项目及会话位置，重新打开时恢复该位置。

规划区使用“总纲会话 / 任务规划会话”页签切换。每个项目分别记住最后访问的概览、规划或工作页面，以及所选会话；切换项目、离开项目管理后重新进入时恢复原位置。总纲与任务规划分别保留最近选择的会话。浏览位置只保存页面和会话标识，不复制聊天内容；记录从本次更新后开始，缺失或已删除的会话按当前项目资料回退。

同一窗口内通过左侧首页或其他入口暂时离开项目时，保留最近项目页面的节点、资料与滚动位置；返回项目入口先同步展示缓存，再后台核对最新资料和权限。原生会话按原有身份接回，不重新发送消息。窗口关闭或源码重新注入后使用保存的浏览位置恢复。

## Skill 管理

Skill 管理可按通用或指定项目筛选。新建时选择归属；也可打开现有托管或外部 Skill，点击“创建项目版本”，选择项目并复制为独立版本。指令及随附脚本、模板、参考资料一起保留，来源不被修改。来源版本或资料变化时显示更新提示，不自动覆盖项目版本。保存和删除检查版本；六项内置 Skill 可编辑、不能删除，外部 Skill 保持只读。

| 调用 | 使用会话 | 工作内容 |
| --- | --- | --- |
| `$better-codex-charter` | 项目总纲会话 | 核实和维护总纲，登记用户对对应版本的确认 |
| `$better-codex-charter-review` | 项目总纲会话 | 审核需求覆盖、必要范围、用户习惯及业务操作逻辑 |
| `$better-codex-plan` | 任务规划会话 | 根据确认总纲规划、修订并转换选定任务 |
| `$better-codex-task-review` | 任务规划或工作会话 | 审核计划或当前绑定任务的覆盖、范围、操作路径、拆分与依赖 |
| `$better-codex-develop` | 工作会话 | 根据当前任务及引用版本开发、代码复核，登记开工和开发完成证据 |
| `$better-codex-test` | 工作会话 | 按任务验收标准测试，登记通过、失败、阻塞及待人工验收项 |

开发与测试 Skill 先通过可信会话绑定读取当前任务、引用资料、版本和阶段记录，沿用对应项目规则。开发完成后可在同一任务的工作会话调用测试 Skill；手工工作项无需为使用 Skill 补建完整规划。报告留在工作会话或已有约定文档，阶段结果通过任务状态工具登记并回读核对。技术验证和用户验收分别记录，未执行的环境或设备验证保留待验收，工具成功不证明报告中的测试真的执行过。

选用 Skill 后，会话持续保持对应职责，普通补充、继续或状态变化不会自动切换阶段。用户在可写工作会话主动选择另一项 Skill 并提出该阶段工作，即构成明确切换和对应授权，不需要另说“结束前一个角色”；助手内部辅助调用结束后回到原职责。总纲、任务规划和只读历史的绑定范围不能通过换 Skill 突破。

总纲和任务可以在修订过程中调用审核 Skill。审核给出需求对应关系、具体问题及最小调整建议，检查是否有遗漏、未经批准的范围或不必要的操作步骤。必要权限和业务完整性仍须保留；用户习惯依据明确要求、旧系统和已有页面，未知内容标为待核实。审核通过不自动确认总纲、转换任务或启动开发；仅审单项任务时不代表整个项目已审完。在工作会话审核总纲时，明确审的是该任务引用版本。

通用 Skill 导出到本机用户 Skill 目录，项目专属 Skill 仅导出到该项目主目录下的 `.agents/skills/`。任务选择与原生发送均校验项目归属。由于原生 Skill 按物理目录发现，共享同一主目录、使用重定向共享路径，或主目录包含其他项目目录时，无法保证专属 Skill 的隔离，系统会阻止对应导出并提示选择独立目录；项目本身和普通会话仍可使用。新增项目造成目录重叠时，已有托管导出先备份再停用，不覆盖外部文件。

任务可以选择 Skill；模型、推理强度、Fast 模式和权限由原生 Codex 管理。旧角色配置保留兼容读取，不再提供角色配置写入入口。

原生输入框加号右侧提供独立闪电按钮，点击开启加速，蓝色高亮表示已开启，再点一次关闭；不支持加速的模型或当前不可用时按钮置灰。旁边提供模型快捷选项，默认包含“6.1 Sol · 中等”和“6.1 Sol · Ultra”。快捷选项可直接左右拖动排序，松开后自动保存，拖动时蓝线标明插入位置，配置窗口沿用相同顺序。点击“配置”可新增、修改名称/模型/强度或删除选项，保存后在本机保留。点击快捷选项同时切换模型和强度，保留当前加速状态；闪电按钮只切换加速。原有模型与强度选择入口继续可用，不支持的组合暂不可选；Ultra 等原生权限确认继续由 Codex 展示。

已绑定的总纲、任务规划和工作会话可通过会话顶部的“解除绑定”恢复为普通 Codex 会话。解除后继续打开同一条原生会话，聊天记录、总纲、计划和任务资料保留；后续对话不再携带任务流上下文、调用绑定专属资料工具或同步任务状态。正在运行或发送结果尚待核对时，需先结束运行或完成核对再解除。项目中仍可新建对应的任务流会话。

## MCP 与数据

保留 `board` 工具，并提供六项项目工具：

| 工具 | 用途 |
| --- | --- |
| `project_context_read` | 读取目录证据、总纲、计划、确认候选以及当前任务版本与阶段记录 |
| `project_charter_save` | 保存单份总纲的草稿章节 |
| `project_charter_confirm` | 使用真实用户消息确认当前总纲 |
| `project_plan_save` | 依据已确认总纲保存计划，不执行任务 |
| `project_plan_convert` | 把明确选中的计划条目转为 todo 任务，不派发执行 |
| `project_task_transition` | 在绑定工作会话登记开发、验收、阻塞与恢复结果 |

页内会话提供对应的 `better_codex_project_*` 线程专属工具，项目编号和线程编号由可信绑定补齐，输入只包含业务参数。原有 MCP 工具继续兼容。首次发送先绑定后发送，重复操作及不确定结果不会自动重放。

工具校验项目和会话绑定、资料版本及操作范围。确认记录只保存必要的消息标识、摘要校验和版本证据；原生聊天仍由 Codex 保存。

`better_codex_project_task_transition` 只接受当前绑定工作任务的业务参数，原生调用不能指定项目、线程或任务编号；兼容 MCP 工具需使用已知的 `project_id`、`thread_id`。总纲、规划及只读历史会话不能调用。每次传入上下文中的 `task.version` 作为 `expected_version`，以及 `action`、事实摘要 `summary`、证据数组 `evidence` 和人工待办数组 `pending_manual`；开发完成和验收结果需要实际证据。上下文的 `task.workflow` 提供阶段、结果、剩余人工项、阻塞前状态及最近记录。

| 状态动作 | 结果 |
| --- | --- |
| `start_development` | 登记真正开工，进入 `in_progress` |
| `development_complete` | 开发与代码复核完成，进入 `in_review` 等待验收 |
| `start_review` | 在有效开发完成后登记开始本轮验收，保持 `in_review`；允许工具认可的历史待审核成果 |
| `review_passed` | 必需技术项通过；有 `pending_manual` 时保留 `in_review`，无人工待办时进入 `done` |
| `review_failed` | 本轮最终结论汇总缺陷、仅提交一次并返回 `in_progress`，不自动执行修复 |
| `block` / `resume` | 登记真实阻塞 / 恢复阻塞前状态；旧任务缺少恢复状态时保守回 `todo`，恢复不代表通过 |

状态工具成功后还要回读上下文，才能报告看板已同步。并发版本冲突先重读，结果不确定先核实，不重放旧请求、不直接改库。人工验收只由用户在界面确认，模型工具不提供代签入口，并拒绝模型清空已经登记的人工项。任务审核 Skill 审的是规划和工作项要求，不登记代码验收结果。

上下文通过 `task.workflow.evidence_valid` 指明当前阶段证据是否仍有效。任务资料改动或重新开工后，旧开发和验收记录不能跨阶段复用；出现 `scope_changed` 或已有真实阶段记录失效时，按当前范围重新走开发开工、开发完成、验收开评和结果登记。初始 `todo`、尚无 workflow 或仅有 `legacy_review` 的证据未成立，不等于资料变更；旧 `in_review` 任务可由 `start_review` 懒初始化并校验，旧状态不能当作通过证据，重新开发后的旧成果也不能替代新的开发完成。开发完成之后必须登记 `start_review` 才开始验收；只有当前 `reviewing` 且开评有效时，才沿用本轮持续测试。

已 `review_passed` 且证据有效、仅剩人工项时，查询状态或补充人工结果不重开评，用户确认入口保持可用。真正重测才明确登记新一轮 `start_review`，实际执行后重新提交结果。恢复阻塞后先回读实际状态与有效性，回到 `todo` 或证据失效时重新开发；未执行的必需技术验证不能靠人工签收代替。结果登记不是测试真实性证明，实际验证与人工操作仍需对应证据。

总纲资料区提供“确认总纲”按钮，点击即登记当前显示草稿的确认；并发修订时拒绝确认旧版本。在绑定的总纲会话中，“当然了，确认”“我确认了”等明确确认短句也会登记并更新确认状态，无需固定口令。疑问、否定和未来确认意图不触发确认。确认后可新建任务规划，不自动生成任务或启动开发。

`C:\Users\admin\.better-codex` 是现有唯一权威数据目录，保存项目总纲、计划、任务及托管 Skill 元数据。托管 Skill 按本机 Skill 目录导出；外部 Skill 不迁入、不覆盖。不复制数据库、凭据或聊天到源码。

本版本移除了远程 Web 页面、远程登录、Relay、Sync 的服务和命令入口；保留本地 Runtime、MCP、原生会话中继及本地固定版本启动入口。

## 本轮保留的执行限制

1. 依赖用于规划展示和提示，没有新增跨任务依赖调度，开工前仍需核实前置成果实际可用。
2. 状态工具校验会话身份、版本、阶段动作及证据字段，但不能自动判断测试内容的真实性；运行、设备和人工验收仍需对应环境的实际证据。
3. 采用阶段状态流程的任务，旧调度结果不再覆盖阶段结果；尚未登记该流程的旧执行器任务仍保留原机制。
4. 多任务修改共享模块时，通过规划明确责任和顺序，没有新增文件锁或隔离机制。

## 编辑位置

- `src/ui/better-codex-ui.js`：已提取的界面代码和样式，保存后自动校验并重新注入。
- `src/ui/native-conversation-adapter.js`：原生草稿、首发绑定和线程专属工具适配，与界面源码组合注入。
- `src/backend/better-codex.cjs`：保留现有打包代码的后台入口，保存后自动重载。后续可逐步拆分模块。
- `src/modules/`：总纲、计划、托管 Skill、工作目录及原生会话模块。
- `src/skills/`：六项内置总纲、规划、审核、开发与验收 Skill 源码。
- `integration/`：启动器、注入、监听、重载协调和迁移/恢复工具。
- `integration/codex-compatibility.json`：已迁出的 Codex 界面选择器、属性、路由及能力适配配置；修改后自动校验并重载。

生成程序、恢复快照和日志在 `.dev/`，不手动编辑。数据仍在 `C:\Users\admin\.better-codex`，不复制进项目，不提交数据库或凭据。

## 日常使用

从原来的 Better Codex 桌面入口启动即可。监听器自动运行；保存 `src` 或 `integration` 下的 JS/CJS 文件后自动生效，无需复制文件或手动编译。连续保存会合并处理。

界面更新保留选中的项目、页签、输入草稿、焦点与滚动位置。后台有运行中的工作时等待空闲，空闲后重载。语法错误保留当前程序；新后台启动失败恢复上一版。

修改 MCP 定义后需通过原生 `config/mcpServer/reload` 刷新宿主工具，再核对六项内置 Skill 与线程工具的实际发现和应用状态；若刷新不可用再重启 Codex，源码监听不会强制结束当前聊天。实际核对结果见 [VALIDATION.md](VALIDATION.md)。

## 命令

在本项目目录运行（无需安装 npm 依赖）：

```powershell
npm start        # 启动本地服务、监听并接入当前 Codex
npm run launch   # 从固定入口打开 Codex
npm run status   # 查看程序、监听器和最近重载状态
npm run repair   # Codex 更新后重新发现安装位置并重新接入
npm test         # 源码、重载及独立 fixture 检查
npm run stop     # 停止本地服务和监听器
npm run rollback # 恢复迁移前安装入口，保留数据库
```

也可以双击项目根目录的 `repair.cmd` 修复接入。`npm run repair` 针对当前环境重新发现并接入；新版 Codex 如果改变界面或会话接口，需要调整接入层，不能保证所有未来版本自动兼容。

独立 HTTP 接线测试为 `node tests/native-backend.cjs`，使用临时 HOME、数据库和工作目录，不发送模型请求。`tests/ui-smoke.cjs` 和 `tests/acceptance.cjs` 对应历史自绘聊天界面，不作为本轮验收步骤。

当前桌面可使用 `node tests/installed-native.cjs --refresh-mcp --check-reload` 核对工具、Skill 和界面重载。它只读取宿主信息、刷新注入并恢复视图，不新建聊天、不发送消息；结果保存为 `.dev/native-planning-acceptance.json`。

历史迁移记录在 `.dev/acceptance.json`、`.dev/startup-acceptance.json` 与 `.dev/data-acceptance.json`，重载诊断在 `.dev/status.json` 与 `.dev/events.jsonl`。原程序、启动配置和经过完整性检查的数据库备份在 `.dev/backups/`。恢复程序不会用旧数据库覆盖当前数据。

本轮实际验收结果及未验证范围见 [VALIDATION.md](VALIDATION.md)。
